# 风电机组 Service BOM —— 代码评审、优化建议与升级路线

> 评审范围：`app.py`、6 个蓝图（projects / bom / materials / compare / assets / backups）、8 个 service、前端 `index.html` + 9 个 JS、部署脚本、SQLite 现状。
> 代码规模：Python 约 4,700 行（不含 .venv），前端 HTML 2,067 行 + JS 约 333 KB。
> 当前数据现状：projects 1 / subsystems 1 / materials 69 / bom_items 66 / material_structures 0；assets 目录 **129 MB**（84 张图 + 34 份 PDF）。

---

## 一、总体评价

**做得好的部分**（请保持）：

- 分层方向正确：`blueprints`（路由）+ `services`（引擎）已经解耦，`register_blueprints` 统一注册，路由路径完全兼容前端。
- 资产解耦设计（图片/手册独立资产库 + 物料主库单点维护）抓住了 Excel 维护 BOM 的真正痛点，是这个系统最有价值的设计。
- 关键破坏性操作（删项目、清主库、导 Excel、拉主库）前都做了 `create_backup_snapshot`，安全意识在线。
- WAL + `busy_timeout` + `conn.backup()` 原子快照，SQLite 用法基本正确。
- 双引擎（Windows waitress / Linux gunicorn）+ 局域网 IP 探测 + 一键 bat，交付体验好。

**核心问题一句话概括**：
> 这是一个**功能完成度很高的单机原型**，但它是**按"单人、可信内网、小数据量"假设写出来的**。一旦真正进入"局域网多工位协同 + 数据持续增长"的生产场景，会同时暴露**安全边界缺失、并发一致性无保护、资产未纳入备份、工程化基建为零**四类风险。

优先级总览：

| 级别 | 问题 | 影响 |
|---|---|---|
| 🔴 P0 | 无认证授权、上传路径穿越、备份不含 assets、无 Git | 数据可能被任意篡改/永久丢失 |
| 🟠 P1 | 外键从未启用、写操作无事务边界、全局单活锁、删除物料留孤儿 BOM 行 | 数据一致性破坏 |
| 🟡 P2 | N+1 查询、全表无分页、逐行 UPDATE、导出文件并发覆盖、129MB 原图直塞 | 数据量上来后变慢/出错 |
| 🔵 P3 | 业务逻辑堆积在蓝图、重复代码、print 代替日志、无测试/CI/锁版本 | 维护成本随规模非线性上升 |

## 二、🔴 P0：安全与数据资产（建议本周内处理）

### 1. 系统完全无认证、无授权
所有 `/api/**` 裸奔，服务默认监听 `0.0.0.0:8000`。局域网内任何人（包括误入的访客网络终端）都能：
- `POST /api/materials/clear` —— **一键清空全局物料主库**；
- `POST /api/project/delete` —— 删除任意工程；
- `POST /api/backup/restore` —— 回滚数据库到任意快照。

**建议**：
1. 短期（1 天）：加最简登录（Flask-Login + 口令文件）+ 全站 `@login_required`，并把 `HOST` 默认改为 `127.0.0.1`，需要局域网共享时再显式开启。
2. 中期：接入企业域账号（LDAP）或内置用户表 + RBAC（`admin` / `engineer` / `viewer`），只读角色禁止所有写接口。
3. 补一张 **`operation_logs` 审计表**（user, action, target, before/after, ip, created_at），所有写接口统一记录。BOM 是技术归档数据，出问题时"谁改的"必须可追溯。

### 2. 上传接口存在路径穿越（真实漏洞）
`blueprints/assets.py:91`：
```python
filename = f"{mat_no}.pdf"          # mat_no 直接来自 request.form，未做任何清洗
dest_path = os.path.join(MANUALS_DIR, filename)
file.save(dest_path)
```
`mat_no` 传 `..\..\..\..\evil` 或 `C:\evil` 即可写到磁盘任意位置。（同一文件的图片分支 `upload_image` 做了 `re.sub` 清洗，手册分支漏了。）

**修复**：统一走一个 `safe_material_filename(mat_no, ext)` 工具函数，并强制只保留 `[A-Za-z0-9._-]`；更稳妥的做法是**用 DB 主键/UUID 作为文件名**，把原始名只存在数据库里。

### 3. 上传无大小与类型白名单校验
`MAX_CONTENT_LENGTH` 从未设置，未校验文件真实 magic bytes（只看扩展名）。建议：
```python
app.config['MAX_CONTENT_LENGTH'] = 50 * 1024 * 1024   # 50MB
```
并对图片用 Pillow `Image.verify()`、对 PDF 校验 `%PDF-` 头。

### 4. 备份只备份数据库，129 MB 的图片与手册完全裸奔
`backups/` 里 6 个快照全是 151 KB 的 `.db`，而 `assets/` 有 **129 MB** 的图片和 PDF。
一旦磁盘故障或误删 assets，**数据库完好但所有物料图/手册引用全部断裂**，且系统无法自愈。

**建议**（重要）：
- 备份包改为 **ZIP：db 快照 + assets 增量/全量**，或至少提供"资产归档"独立任务；
- 增加**定时自动备份**（每日 + 每次退出前），当前只在破坏性操作前触发；
- 备份保留策略从"最多 30 个"升级为"保留最近 7 天每日 + 最近 8 周每周 + 手动永久"，并按总容量上限裁剪；
- 每年做一次**恢复演练**（现在没有 `/api/backup` 的完整性校验，manifest 与实际文件可能不一致）。

### 5. 项目无版本控制（连 `.git` 都没有）
当前工作区 **没有 git 仓库**，全部代码只有一份磁盘副本，且根目录有 `__pycache__` 与 `.venv` 混在一起。
**立刻执行**：`git init` + `.gitignore`（排除 `.venv/`、`__pycache__/`、`data/`、`assets/`、`backups/`、`uploads/`、`exports/`）+ 首次提交。这是所有后续重构的安全网，优先级等同于修漏洞。

### 6. 硬编码密钥与异常信息泄露
- `app.py:20`：`SECRET_KEY = 'service-bom-secret-key-2026'` 硬编码，任何拿到代码的人可伪造 session/cookie。应改 `os.environ.get('SECRET_KEY', os.urandom(24).hex)` 并写入 `.env`（不入库）。
- `app.py:39`：全局异常处理器把 `str(e)`（可能含数据库路径、SQL、栈信息）直接返回给前端。应改为 `logger.exception()` + 返回通用文案 + `error_id` 供排查。

## 三、🟠 P1：并发一致性与数据完整性（下个迭代处理）

### 7. 外键约束从未生效
全库搜 `PRAGMA foreign_keys`，只在 `database.py` 的一次性迁移里出现过 `OFF/ON`，`get_db()` 里**从未开启**。
也就是说 `bom_items → materials`、`subsystems → projects` 等所有 `FOREIGN KEY ... ON DELETE CASCADE` **全是装饰**，没有任何约束力。

**建议**：在 `get_db()` 里加 `PRAGMA foreign_keys = ON`（注意：SQLite 需在每个连接上执行，且必须在事务外）。开启后要回归测试现有删除逻辑（例如 `delete_project` 已手动删子表，仍然安全）。

### 8. 删除物料会留下孤儿 BOM 行
`materials.py:delete_material` 只删了 `material_structures` 和 `materials`，**没有处理 `bom_items`**。
结果：BOM 表里残留指向已删除物料的行，导出时名称/规格/图片全空，且不会被任何"未引用物料"统计发现。

**建议**：删除前先查引用（`get_material_usage` 已有现成 SQL），有引用则**强制二次确认**或改为"软删除 + 标记停用"，而不是静默产生孤儿数据。

### 9. 写操作没有事务边界，多步修改不是原子的
典型：`bom.py:add_bom_item` 执行 `UPDATE row_num 预留空位 → INSERT 父行 → INSERT N 个子行 → renumber`，全程靠 SQLite 的隐式事务。
在 waitress 8 线程 + 局域网多工位下，两个并发的插入/移动/删除会让 `row_num` 错乱，或触发 `database is locked`。

**建议**：
- 引入 `BEGIN IMMEDIATE` 显式写事务（可用一个 `@with_write_tx` 装饰器或上下文管理器），把"检查 + 修改 + 重编号"包进同一个事务；
- `get_db()` 改为 **Flask `g` + `teardown_appcontext` 自动关闭连接**（现在有若干提前 `return` 的分支没关连接）；
- 所有写接口统一加一个**进程内 `threading.Lock()` 串行化写**（SQLite 单写者模型的实用做法），或改为"单写线程 + 任务队列"。

### 10. 项目锁是"全局单活"模型，无法多人并行
`unlock_project_api` 里 `UPDATE projects SET is_locked = 1 WHERE id != ?` —— 解锁 A 会把**所有其他工程全部锁上**。
意味着局域网里**两个人无法同时编辑两个不同机型**，而且没有任何超时释放机制（客户端崩溃 → 工程永久锁定，需要人工改库）。

**建议**：升级为真正的**带租约的锁**：
```sql
locked_by TEXT, locked_at TIMESTAMP, lock_expires_at TIMESTAMP
```
- 按项目加锁，支持"查看谁在编辑"；
- 锁有过期时间（如 30 分钟心跳续约），异常退出自动释放；
- 或者更进一步：去掉悲观锁，改用**乐观锁**（`bom_items.version` / `subsystems.revision`），提交时校验版本号，冲突给出合并提示。

### 11. `check_project_unlocked` 存在 TOCTOU 窗口
它**自己开一个连接**查一次锁状态，然后关闭；真正的写入在另一个连接/事务里。
"检查通过"到"实际写入"之间，别的请求完全可能把工程锁上。这也是第 9 点的衍生问题，统一到同一事务里解决。

### 12. 导入器重复导入会产生重复数据
`services/importer.py` 对每个 sheet 无条件 `INSERT INTO subsystems`，BOM 行也是无条件 `INSERT`。
同一个 Excel 导入两次 → 子系统翻倍、BOM 行翻倍。

**建议**：改为按 `(project_code, subsystem_name)` 做 UPSERT，导入前提供"覆盖 / 追加 / 新建工程"三选一；并在导入结果里返回新增/更新/跳过的计数。

## 四、🟡 P2：性能与稳定性

### 13. 典型的 N+1 查询
- `data_audit.get_duplicate_materials_report()`：对每个物料跑 2 条查询（69 个物料 = 138 次往返）。物料到 5,000 条时是 1 万次。
- `database.get_material_tree()`：递归展开总成，每层一次查询，深层级总成会放大。

**建议**：
- 审计改用 `GROUP BY` 一次性聚合引用关系（一条 SQL 拿全部 `material_no → ref_count, projects`）；
- `get_material_tree` 改为"一次性取出 `parent_material_no IN (...)` 的全部层级，在内存建邻接表后再递归"，并加**深度上限**（如 10 层）防环。

### 14. 主库列表无分页 + 每行 4 个子查询
`materials.py:get_materials` 对每行执行 `child_count / usage_project_count / usage_total_count / projects_json`（含 `json_group_array` 嵌套子查询），且**一次性返回全表**。

**建议**：加 `page / page_size` 分页；把 4 个子查询合并为 1~2 条 `LEFT JOIN + GROUP BY`；搜索字段上加索引（考虑 SQLite FTS5 做物料号/名称/规格的模糊搜索，比 `LIKE '%x%'` 快一个量级）。

### 15. 逐行 UPDATE 的重编号
`renumber_subsystem` 对每行执行一条 `UPDATE`。1,000 行的 Sheet 就是 1,000 次写。

**建议**：SQLite 3.25+ 支持窗口函数（当前环境是 **3.53.1**，完全支持），一条 SQL 搞定：
```sql
WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (ORDER BY row_num, id) AS rn FROM bom_items WHERE subsystem_id = ?
)
UPDATE bom_items SET row_num = (SELECT rn FROM ranked WHERE ranked.id = bom_items.id)
WHERE subsystem_id = ?;
```
或至少用 `executemany()` 批量提交。

### 16. 导出产物路径写死，并发导出会互相覆盖
`projects.py:export_excel` 固定写到 `exports/<机型名>.xlsx`，两个用户同时导出同一机型 → 同一路径竞争写，轻则内容错乱，重则文件损坏；且 `exports/` 只增不减。

**建议**：写到 `tempfile` 生成的唯一文件名，`send_file` 后清理；或用 `io.BytesIO` 直接内存返回（工程包 `/api/project/<id>/export_file` 已经是内存方式，Excel 导出应保持一致）。再加一个定时清理任务（保留最近 N 个 / N 天）。

### 17. 129 MB 原始图片直接塞进 Excel 和离线 ZIP
`exporter.py` 直接把原图（可能有几 MB 一张的照片）按格子缩放写入 xlsx；离线包也直接打包原图。
一个中等机型导出几十 MB 是常态，邮件发不出去、现场平板打不开。

**建议**：
- 上传时生成**两级图**：缩略图（列表用，≤300px）和展示图（≤1200px），DB 存两个路径；
- 图片统一转 WebP/JPEG 并做质量压缩（Pillow 已是依赖）；
- 离线包提供"标准版 / 精简版（只含缩略图）"两种规格。

### 18. Excel 导入器手写 XML 解析，脆弱
`services/importer.py` 用 `zipfile + ElementTree` 手撕 xlsx，只处理了 `t="s"`（sharedStrings）。
遇到 **inlineStr**（WPS、部分工具导出的表格常见）、公式缓存值、日期序列号时会**静默丢数据**。
另外 `if not mat_no: mat_no = f"AUTO_{sub_name}_{row_idx}"` 会往主库塞垃圾编码。

**建议**：既然已经依赖 openpyxl，导入改用 `openpyxl.load_workbook(..., data_only=True, read_only=True)`；图片仍走 zip 直取（openpyxl 拿不到锚定行时需要），但把"行列解析"交给 openpyxl，可维护性提升巨大。同时给物料号为空的行打 warning 而不是造号。

### 19. 导出列位置硬编码
`exporter.py` 里 A~P 列、封面 A2/A4/C6/C7/C8/A9/A11、签字页 C33/D33… 全是魔数，图片列还要靠 Row3 表头猜。
模版一改版就要改代码。

**建议**：抽一份 `config/template_mapping.json`（封面字段映射、BOM 列映射、签字行号），代码读配置。

### 20. 离线包临时目录可能泄漏
`offline_packager.py` 用 `tempfile.mkdtemp()`，但 `os.rmdir(temp_dir)` 在目录非空时静默失败（还有个裸 `except: pass`）。
**建议**：改用 `with tempfile.TemporaryDirectory() as td:`。

## 五、🔵 P3：代码结构与工程化

### 21. 业务逻辑大量堆积在蓝图里
`blueprints/projects.py` **1,170 行**、`materials.py` 713 行，里面直接写 SQL 做"复制工程""复制 Sheet""主库拉取"。
蓝图应只做「参数校验 → 调 service → 组装响应」。

**建议**：新建 `services/project_service.py`（复制/重命名/锁定/删除）、`services/bom_service.py`（增删改移/重编号）、`services/material_service.py`，蓝图瘦身为 50~150 行/文件。

### 22. 明显的重复代码，值得立刻抽公共函数
- **"代号去重后缀"**逻辑出现 4 次：`save_project`、`copy_project`、`import_project_from_file`、`copy_subsystem` → 抽 `unique_project_code(base)` / `unique_name(base, existing)`。
- **"复制一个 Sheet 的所有 BOM 行"**在 `copy_project` 和 `copy_subsystem` 里几乎一字不差 → 抽 `copy_bom_rows(src_subsystem_id, dst_subsystem_id, cursor)`。
- **"工程信息展示名"`system_name or code or name`**散落十余处 → 抽 `project_display_name(proj)`。
- **封面/子系统标题的命名规则**（`{code}{sub_name}变桨轴承润滑系统`）在 exporter 里重复 3 次。

### 23. 响应格式不统一
有的接口返回 `{'success': True, ...}`，有的返回 `{'error': ...}`（无 success 字段），有的直接返回数组（`get_projects`、`get_bom_items`）。
前端必须写两套兼容逻辑。

**建议**：统一封装
```python
def ok(data=None, **extra): return jsonify({'success': True, 'data': data, **extra})
def fail(msg, code=400): return jsonify({'success': False, 'error': msg}), code
```
并配套统一错误码表。

### 24. 用 `print()` 代替日志（共 40 处）
目前全项目 **0 处** `import logging`，异常全靠 `print()` 和 `except: return str(e)`。
生产环境出问题无法定位。

**建议**：引入 `logging` + `RotatingFileHandler`（写 `logs/app.log`），请求级 `request_id`，关键写操作记 INFO，异常记 `logger.exception()`。

### 25. 缺少配置管理
端口 8000、备份保留 30、waitress 8 线程、导出行高 70、公司名"上海电气风电集团股份有限公司"、表单号 `FDJL-JS-037` 全部硬编码散落各处。

**建议**：建 `config.py`（`DevConfig / ProdConfig`）+ `.env`，业务常量（公司名、表单号、默认单位）集中到 `config/constants.py`。

### 26. 数据库迁移是手写的 PRAGMA + ALTER，脆弱
`init_db()` 里用 `PRAGMA table_info` 判断列是否存在、手工重建表改列类型（`seq_num` INT→TEXT），
逻辑分支互相依赖（`cols` 在 ALTER 之前/之后的可见性），加字段时要小心翼翼。

**建议**：
- 加一张 `schema_version(version INTEGER, applied_at)` 表，把每次变更写成**幂等的顺序迁移脚本**（`migrations/001_xxx.sql`），启动时按版本号依次执行；
- 或直接引入 `alembic`（配合 SQLAlchemy）/`yoyo-migrations`（纯 SQL，对 SQLite 友好）。

### 27. 零测试、零 CI、依赖未锁定
- 项目里**没有任何测试文件**。BOM 重编号、层级计算（`compute_bom_hierarchy_numbers`）、上移下移（`move_bom_item` 的块移动算法）、数量解析（`parse_float_qty`）都是**极易回归的核心算法**，必须有单元测试。
- `requirements.txt` 全用 `>=`，换台机器装出来的版本可能完全不同 → 加 `requirements.lock`（`pip freeze` 或 `uv pip compile`）。
- 建议加：`ruff` + `black`（代码风格）、`pytest`（测试）、`pre-commit`、`GitHub Actions`（提交即跑 lint+test）。

## 六、数据模型的升级建议

### 28. `qty` 是 TEXT，无法在 SQL 层聚合
现在统计单机总量只能把全表拉到 Python 里 `float()` 累加（`comparator.py` 就是这么干的）。
**建议**：新增 `qty_num REAL` 冗余列（写入时同步），或把数量规范化为 `REAL + unit` 两列，让 `SUM/GROUP BY` 直接在 SQL 完成，也为后续"整机成本汇总""按供应商统计用量"铺路。

### 29. 缺少时间戳与软删除
`materials`、`bom_items` 都没有 `created_at / updated_at / deleted_at`。
主库同步只能全量比对，无法做增量同步。

**建议**：补 `created_at / updated_at`（SQLite 用触发器或应用层写入），`materials` 加 `status`（`draft/active/obsolete`）与 `deleted_at` 软删除，**物料停用但不删除**，历史 BOM 仍可追溯。

### 30. 缺少唯一约束
`subsystems(project_id, name)`、`signatures(project_id, role)` 都可能重复（后者靠 "先 DELETE 再 INSERT" 规避，但并发下仍可能重复）。
**建议**：补 `UNIQUE` 约束，配合第 7 点开启外键后一并生效。

### 31. 【重要升级】缺少「基线 / 版本快照」概念
现在的"工程"就是唯一版本，ECN 只是几行文字记录，**没有 BOM 的历史快照**。
工程改了就改了，无法回答"三个月前发布的那一版 BOM 长什么样"。

**建议**新增：
```sql
project_versions(id, project_id, version_no, status[draft/released],
                  snapshot_json, created_by, created_at, release_note)
```
- 发布时把完整 BOM（含层级、数量、图号、当时的物料主数据快照）序列化存一份；
- 比对引擎升级为支持 **"基线 vs 基线"**、**"基线 vs 当前"**，而不只是"工程 A vs 工程 B"；
- ECN 记录关联到具体版本，形成"变更申请 → 审批 → 发布 → 归档"的闭环。

这是让系统从"编辑工具"升级为"工程数据管理平台"的关键一步。

### 32. 替代料是单字段，无法表达替代链
`substitute` 只是一个文本字段。实际业务里"原厂停产后用 A 替代，A 缺货用 B 替代"是链式的，且替代有方向性（单向/双向）和有效期。
**建议**：新增 `material_substitutions(parent_no, substitute_no, direction, priority, effective_date, remark)`。

## 七、前端建议

### 33. 2,067 行 HTML + 9 个全局脚本，无模块化
`bom.js` 109 KB、`material.js` 79 KB、`project.js` 53 KB，全部靠 `<script>` 顺序加载、全局函数互相调用（`window.xxx` 十余处）。
风险：加载顺序敏感、命名冲突、无法按需加载和压缩。

**建议（分两步）**：
1. 短期：全部改为 ES Modules（`<script type="module">`），每个文件显式 `export/import`，`main.js` 作为入口；
2. 中期：引入 **Vite + Vue3**（或 React），把 BOM 表格、物料卡片、比对报告做成组件。BOM 表格尤其需要**虚拟滚动**（几千行时 DOM 会卡死）。

### 34. 静态资源无版本缓存策略
改了 JS 用户可能拿到旧缓存。
**建议**：文件名加 hash（`bom.a1b2c3.js`）或加 `?v={{ build_id }}`；生产关闭 `TEMPLATES_AUTO_RELOAD`（现在无条件开启，有性能损耗）。

### 35. 缺少前端体验细节
- 所有写操作无 loading 态与失败重试，网络抖动即丢数据；
- 表格无"撤销"（尤其上移/下移/删除应支持 Ctrl+Z 或至少"撤销上一次操作"）；
- 无未保存离开提醒；
- 建议加**乐观更新 + 冲突提示**（配合后端的乐观锁）。

## 八、部署与运维

### 36. 缺少健康检查与监控
**建议**：加 `/api/health`（返回 DB 可连、版本、磁盘余量、assets 目录大小），配合 nginx/Docker healthcheck；
关键路径（导入/导出/比对/备份）记录耗时，慢操作打点。

### 37. 备份与资产应纳入运维计划
见第 4 点。另外建议：
- `backup_manager` 增加**备份完整性校验**（记录 db 的 `PRAGMA integrity_check` 结果和文件 SHA256）；
- 提供"一键导出全部资产 ZIP"给运维做冷备。

### 38. Windows 侧可服务化
现在是"开个黑框跑 bat"。
**建议**：用 NSSM 或计划任务把 waitress 注册为 Windows 服务，开机自启、崩溃自拉；同时保留现在的 `启动系统.bat` 给临时场景。

### 39. Dockerfile 与 requirements 需分环境
`gunicorn`（Linux）和 `waitress`（Windows）混在同一份 requirements 里。
**建议**：拆 `requirements/base.txt` + `requirements/windows.txt` + `requirements/linux.txt`；Docker 镜像只装 Linux 侧依赖。

## 九、分阶段落地路线图

### 第 1 阶段：止血（1 周）
1. `git init` + `.gitignore` + 首次提交；
2. 修 `upload_manual` 路径穿越（统一文件名清洗函数）；
3. `SECRET_KEY` 环境变量化；异常响应不再回显 `str(e)`；
4. 加最小登录 + 写接口鉴权（`HOST` 默认改 `127.0.0.1`）；
5. 备份纳入 assets（至少提供资产归档 + 每日自动备份）。

### 第 2 阶段：稳基（2~3 周）
6. `get_db()` 开启 `foreign_keys`，改为 `g` + `teardown` 自动关连接；
7. 写操作统一事务（`BEGIN IMMEDIATE`）+ 进程内写锁；
8. 修 `delete_material` 孤儿 BOM 行；导入改 UPSERT；
9. 引入 `logging` + 统一响应封装 + 配置管理（`config.py` + `.env`）；
10. 补齐核心算法单元测试（重编号 / 层级计算 / 移动 / 数量解析）+ ruff/black + pre-commit。

### 第 3 阶段：提速与重构（1~2 个月）
11. service 层拆分（project/bom/material 三个 service），蓝图瘦身；
12. 抽取重复逻辑（代号去重 / 复制 BOM 行 / 展示名 / 模版列映射配置化）；
13. 消除 N+1（审计聚合查询、物料树内存递归）、主库分页 + FTS5 搜索；
14. 重编号改用窗口函数；导出改内存流 + 临时唯一文件；
15. 图片分级压缩（缩略图 + 展示图），离线包体积下降一个数量级；
16. 项目锁升级为带租约的锁 / 乐观锁。

### 第 4 阶段：平台化升级（3~6 个月，按业务价值排序）
17. **基线/版本快照 + 发布审批流**（价值最高，让 BOM 可追溯、可审计）；
18. 用户体系 + RBAC + 完整操作审计；
19. 数据模型增强：`qty_num`、时间戳、软删除、物料状态、替代链；
20. 前端模块化（Vite + Vue3）+ 虚拟滚动表格；
21. 存储抽象层（现在本地目录，未来可换 MinIO/OSS），文件按内容哈希去重；
22. **对外集成**：物料主库与 ERP/PLM（SAP / Teamcenter）双向同步接口，导出格式适配下游系统；
23. **选型判断点**：如果并发写用户超过 5 人或 `bom_items` 超过 10 万行，建议把 SQLite 换成 PostgreSQL（DAO 层抽象做好后切换成本可控）；在此之前 SQLite + 单写队列完全够用。

## 十、如果只做三件事

1. **`git init` + 备份纳入 assets** —— 防止不可逆的数据/代码损失；
2. **修上传路径穿越 + 加登录鉴权** —— 堵住最现实的安全口子；
3. **写操作统一事务 + 开启外键** —— 让多工位协同下的 BOM 数据不再莫名其妙错乱。
