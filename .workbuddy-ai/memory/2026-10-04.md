# 2026-10-04

## 全量代码评审（Service BOM 系统）
产出：`docs/代码评审_优化与升级建议.md`（P0~P3 分级 + 四阶段路线图）。

关键结论（后续改动请对照）：
- 项目**无 git 仓库**，所有重构前应先 `git init` + `.gitignore`（排除 .venv/__pycache__/data/assets/backups/uploads/exports）。
- **P0 漏洞**：`blueprints/assets.py:91` upload_manual 用未清洗的 `mat_no` 拼文件名 → 路径穿越；全站无鉴权且默认 `0.0.0.0`；`SECRET_KEY` 硬编码；异常响应回显 `str(e)`。
- **备份只备份 DB（151KB）**，assets 有 129MB 图片/PDF 未纳入备份。
- **外键从未启用**：`get_db()` 无 `PRAGMA foreign_keys = ON`，schema 里所有 FK/ON DELETE CASCADE 无效；`delete_material` 不处理 bom_items → 孤儿 BOM 行。
- 写操作（bom add/move/delete + renumber）无显式事务边界；`check_project_unlocked` 独立连接 → TOCTOU。
- 项目锁是"全局单活"（解锁 A 锁全场），无法多人并行编辑不同机型，且无超时释放。
- 性能隐患：`data_audit` / `get_material_tree` N+1；`/api/materials` 无分页且每行 4 子查询；`renumber_subsystem` 逐行 UPDATE（SQLite 3.53 支持窗口函数可优化）；导出写死 `exports/<name>.xlsx` 并发会覆盖。
- importer 手写 xlsx XML 解析，未处理 inlineStr → 可能静默丢数据。
- 前端：index.html 2067 行 + 9 个全局脚本（bom.js 109KB），无模块化、无构建、无缓存 busting。
- 数据现状：projects 1 / subsystems 1 / materials 69 / bom_items 66 / material_structures 0。

## 项目约定 / 已知偏好
- 技术栈：Flask 蓝图 + 原生 sqlite3 + openpyxl + Pillow；Windows 用 waitress，Linux 用 gunicorn。
- 交付形态是给风电工程师双击 bat 启动的局域网单机系统，改动需保持"一键启动"体验。
